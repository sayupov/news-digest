# NEWS & EVENTS INTELLIGENCE 4.0

Ежедневная сводка новостей и еженедельный обзор в Telegram. Проект использует **Python 3.12, GitHub Actions, RSS/Atom, GitHub API, Bluesky API, YouTube Atom, iCalendar, Gemini API и Telegram Bot API**. Для базового сценария VPS и установка дополнительных Python-пакетов не требуются.

## Что действительно реализовано

- Каждый день в 08:00 по Asia/Oral (03:00 UTC) — ежедневный дайджест; по воскресеньям в 17:00 (12:00 UTC) — недельный обзор. GitHub Actions **не гарантирует запуск с точностью до минуты**, возможны задержки.
- Сбор RSS/Atom и публикаций с YouTube, GitHub, Bluesky; дополнительное чтение разрешённых каналов Telegram через отдельного бота. Проверка дат, фильтрация и ранжирование по ИИ-агентам, GovTech, AgriTech, новым инструментам и исследованиям.
- Попытка извлечь фрагменты непосредственно из публикаций (где доступен открытый HTML). **Это не независимая проверка истинности утверждений**. Закрытые статьи, сложный JavaScript и paywall могут не обработаться.
- Сбор событий из публичного календаря iCalendar. У событий должны быть указаны дата и описание; дата считается *сообщённой календарём*, а не независимо подтверждённой. Отменённые события исключаются, когда календарь корректно содержит `STATUS:CANCELLED`.
- Ссылки на Astana Hub и каталог AI-конференций как дополнительные страницы для ручной проверки: **они пока не парсятся в список событий автоматически**.
- Генерация структурированного JSON с Gemini; программная проверка ID источника, точной цитаты и числовых токенов. Это уменьшает часть ошибок генерации, но **не доказывает истинность или корректную интерпретацию публикации**.
- В Telegram видны цитаты, источники, отличия между фактами по сообщению источника и анализом, следующие действия, статус источников.
- `state.json`: история для снижения повторов между ежедневными выпусками. Учитываются **только публикации, реально попавшие в отчёт после успешной отправки**. Не содержит текста новостей, личных данных или токенов. Недопустимо использовать для конфиденциальных задач без дополнительного аудита.
- Offline-тесты на парсер, дедупликацию, события, генерацию, отказ отправки и сохранение истории.

## 1. Структура репозитория

```text
.github/workflows/digest.yml   <-- ОБЯЗАТЕЛЬНО такое расположение
config.json
digest.py                       <-- без пробела в начале имени
tests/test_digest.py
README.md
.gitignore
.env.example
```

**Важно:** файл из старого проекта `digest.yml.txt` необходимо заменить именно на `.github/workflows/digest.yml`. GitHub Actions **не увидит** `.yml.txt` в корне. Уберите из репозитория старые workflow, которые отправляют тот же отчёт, иначе будут дубликаты.

## 2. Как обновить проект в GitHub

1. Откройте ваш репозиторий на GitHub.
2. Загрузите содержимое архива, **сохранив вложенные каталоги и имена файлов**. При загрузке через веб-интерфейс проверьте отдельно `.github/workflows/digest.yml`; иногда удобнее создать его через `Add file → Create new file` и вписать имя `.github/workflows/digest.yml`.
3. Убедитесь, что в корне находятся `digest.py` и `config.json`, а тесты — в `tests/`.
4. Зайдите в **Settings → Secrets and variables → Actions → Repository secrets**. Создайте или проверьте:
   - `GEMINI_API_KEY` — ключ Gemini API.
   - `TELEGRAM_BOT_TOKEN` — токен вашего Telegram-бота.
   - `TELEGRAM_CHAT_ID` — ID личного диалога или группы (боту нужен доступ и право отправки).
5. В **Settings → Actions → General → Workflow permissions** убедитесь, что политика репозитория допускает запись истории (`contents: write`). Если организация запрещает запись, отчёт может отправляться, но история не сохранится; замените хранение state.json подходящим разрешённым способом.
6. Откройте **Actions → News & Events Intelligence 3 → Run workflow**. Для первого запуска выберите `news` и **dry_run = true**: в логах должны появиться подготовленный промпт и отобранные мероприятия, без отправки в Telegram.
7. Повторите запуск с **dry_run = false**. Проверьте сообщение в Telegram и зелёный статус workflow. После успешного ежедневного запуска появится `state.json` или обновится существующий.
8. На следующий день сравните отчёт с предыдущим: опубликованные новости должны по возможности не повторяться, а новые — появляться.

## 3. Настройки config.json

- `timezone`: `Asia/Oral`.
- `hours_back`: окно поиска публикаций, по умолчанию 96 ч, **но повторные публикации подавляет `state.json`**.
- `weekly_hours_back`: семь дней.
- `max_news_for_ai`: сколько новостей передавать Gemini (не сколько он обязан опубликовать).
- `max_article_fetch`: сколько HTML-страниц попытаться прочесть.
- `event_days`: горизонт поиска событий в календаре.
- `feeds`: новости, лучше от надёжных источников.
- `event_calendars`: **URL открытых `.ics`**, не обычные страницы сайта. Неправильный URL появится среди ошибок получения.
- `event_watch_pages`: ссылки на афиши для самостоятельной проверки (без автоматического извлечения отдельных событий).

Не добавляйте служебные документы или персональные данные в RSS, поля конфигурации, промпты или логи. Полученные фрагменты статей передаются в API Gemini.

## 4. Локальная проверка (без ключей)

```bash
python -m unittest discover -s tests -v
python -m py_compile digest.py
```

Для просмотра отобранных материалов без отправки в Telegram:

```bash
DRY_RUN=1 python digest.py news
```

Эта команда **обращается к внешним RSS/ICS**, поэтому требует доступа к интернету, но не вызывает Gemini или Telegram.

## 5. Отладка

- `Gemini ... quota`: проверьте разрешённые модели, квоту и тариф в Google AI Studio. Модель можно сменить через **Repository variables → `GEMINI_MODEL`**; по умолчанию `gemini-3.8-flash`. Поддержка бесплатного тарифа и лимиты зависят от Google и вашего проекта.
- `Calendar unavailable`: проверьте доступность `.ics` URL. Отказ одного источника не останавливает весь сбор.
- `No grounded factual items`: Gemini вернул сведения без достаточной цитаты или с неподтверждёнными числами, поэтому отчёт сознательно **не отправлен**.
- `Telegram credentials missing`: перепроверьте три секрета, токен и ID чата. **Не публикуйте их** в коде, коммитах или скриншотах.
- `git push` / `403`: проверьте workflow permissions и ограничения ветки (branch protection). Telegram мог получить сообщение, но история не сохранится — это может вызвать повтор в следующем выпуске.
- Нет материалов AgriTech или Казахстана: это может означать недостаток подходящих публикаций в выбранном окне, а не отсутствие событий в действительности.
- Нет мероприятий: дополните рабочие ICS-календари; каталог Astana Hub и Linux Foundation пока вынесен в ссылочный раздел.

## 6. Ограничения и безопасность

1. **Недостаточно для гарантии «10/10» без живых проверок.** Все тесты offline, взаимодействие с реальными GitHub Secrets, Gemini и Telegram требует запуска в вашей учётной записи.
2. Подтверждение точной цитаты из полученного текста **не равно независимому фактчекингу**. Ложная статья может содержать точную цитату; вопросы с общественным или государственным значением следует проверять по первоисточнику и нескольким независимым источникам.
3. Подключённый календарь событий — сторонний агрегатор, не официальный организатор. Сверяйте даты и регистрацию перед поездкой.
4. Не все события с повторениями `RRULE` разворачиваются, а повторяющиеся экземпляры с `RECURRENCE-ID` пропускаются. Это ограничение текущего парсера.
5. Скрипт не обходит paywall, логины и JavaScript-защиту сайтов. Не загружайте документы с ограниченным доступом.
6. Для нескольких Telegram-сообщений возможна частичная доставка при сетевом сбое. После неудачной отправки история не обновляется, поэтому повторный запуск может дублировать первые фрагменты. Полная идемпотентность потребовала бы дополнительного механизма хранения статусов сообщений.
7. GitHub Actions может запускаться с задержками. Не используйте такой планировщик для юридически значимых сроков или критичных уведомлений.
8. Расходы Gemini API зависят от тарифного плана, фактических токенов и включённого биллинга. Следите за квотами и бюджетом проекта.

## Исправление сбоя Gemini HTTP 503 (версия 3.1)

Код `HTTP 503 from generativelanguage.googleapis.com` указывает на временную
недоступность или перегрузку Gemini API, не на ошибку RSS.

Исправления:
1. Запрос к Gemini автоматически повторяется до 5 раз с экспоненциальной задержкой,
   случайным разбросом и учётом заголовка `Retry-After`.
2. Если первая модель продолжает возвращать временные ошибки, используется резервная
   модель `gemini-3.5-flash-lite` (от того же провайдера и с тем же ключом).
3. Если сервис всё равно недоступен, пользователь получает в Telegram **резервный
   выпуск без ИИ** с заголовками, аннотациями RSS и календарными событиями.
   Он специально отмечен как непроверенный; искусственный анализ не подставляется.
4. В память записываются только материалы из действительно отправленного выпуска.
5. Ошибки доступа `400/401/403/404` от Gemini **не скрываются**, они завершают запуск
   с сообщением в GitHub Actions, поскольку требуют проверки настроек.
6. Ошибки `403` при чтении веб-страниц не являются основанием отключать источник RSS.

Переменные GitHub Actions (Settings → Secrets and variables → Actions → Variables):
- `GEMINI_MODEL`: основная модель (необязательно, по умолчанию `gemini-3.8-flash`).
- `GEMINI_FALLBACK_MODELS`: список резервных через запятую (необязательно).
  Модели имеют разные квоты и стоимость, проверьте их в Google AI Studio.
- `GEMINI_RETRIES`: число попыток от 1 до 6 (по умолчанию 5).
- `ALLOW_EMERGENCY_DIGEST`: `1` для резервного выпуска (по умолчанию).

Чтобы убедиться в работе исправлений, откройте **Actions → News & Events Intelligence 4.0
→ Run workflow**, `mode=news`, `dry_run=false`. Запустите только один workflow
и проверьте успешную доставку в Telegram, затем файл `state.json` в репозитории.

Локальный тест без внешних ключей: `python -m unittest discover -s tests -v`.

Важно: наличие резервной модели не гарантирует, что она доступна в вашем проекте
или входит в бесплатный лимит. Резервный выпуск без ИИ позволяет не терять сам
доклад в случае временной недоступности сервиса.


## 7. Социальные источники (версия 4.0)

В версии 4.0 новости поступают не только с сайтов. Они объединяются в один список и фильтруются по дате, темам и истории публикаций. Каждый пункт отчёта отмечает платформу-источник. **Пост и описание видео — это заявление автора, а не независимое подтверждение факта.**

### Работают из коробки, без дополнительных ключей

- **YouTube**: `youtube_feeds` — Atom-ленты видеоканалов, а не транскрипты и не просмотр видео. В конфигурации включён официальный Google for Developers (channel ID подтверждён документацией Google). Добавление канала: найти его channel ID `UC...` и вставить `https://www.youtube.com/feeds/videos.xml?channel_id=UC...`.
- **GitHub**: `github_repositories` — новые опубликованные релизы (черновики и prerelease исключены). Сразу включены LangChain, n8n и Anthropic SDK. Публичный GitHub API без токена обычно ограничен 60 запросами в час на IP; при HTTP 403/429 источник пропускается и фиксируется в диагностике. Это релизы кода, не обязательно новые модели или продукты.
- **Bluesky**: `bluesky_accounts` — публичные записи указанных аккаунтов через официальный endpoint `public.api.bsky.app`. Настроены `hf.co` (Hugging Face) и `langchain.bsky.social` (LangChain). Репосты и ответы, не принадлежащие выбранному автору, пропускаются. Публичный API может вводить ограничения.

### Telegram: по желанию, без обхода ограничений

1. Создайте **второго бота** в BotFather; основной бот для отправки дайджеста остаётся прежним.
2. Добавьте нового бота в каналы, которыми управляете или где администратор согласен предоставить доступ. Бот не может по своему токену читать произвольные сторонние каналы.
3. Добавьте Telegram Secret `TELEGRAM_SOURCE_BOT_TOKEN` в **Settings → Secrets and variables → Actions**. Не вписывайте секрет в JSON и не публикуйте его.
4. В `config.json` внесите разрешённые числовые ID каналов в `telegram_channel_ids`, например `[-1001112223334]` (число вымышленное и **не является действующим каналом**). Для включения реального канала потребуется его ID.
5. Бот получает `channel_post` через `getUpdates` при отсутствии активного webhook. Для формирования прямой ссылки канал должен иметь публичный username. Сообщения приватных каналов без публичного URL сознательно исключаются.
6. Читатель хранит последний `update_id` в `state.json` после успешной отправки дайджеста. Telegram хранит обновления ограниченное время; эта схема не гарантирует полный архив. Не используйте второго бота в другой программе, одновременно потребляющей его `getUpdates`.
7. При `dry_run=true` скрипт не подтверждает обработку очереди и не изменяет `state.json`.

**Не подключены автоматически:** Instagram, LinkedIn, X, Reddit. Для них нужны отдельные законные способы чтения и в ряде случаев платные/ограниченные API. Не следует использовать обход авторизации, случайные парсеры или публичные прокси с передачей токенов.

### Изменения в отчёте

- Новости RSS, видео-анонсы, GitHub-релизы и посты Bluesky/Telegram попадают в общий ранжированный набор с меткой платформы.
- Разнообразие источников учитывается при выборе: по возможности попадает хотя бы одна подходящая запись с каждой доступной новой платформы, но фиктивное присутствие не создаётся.
- Ошибка одного источника не блокирует остальные; в диагностике отображается статус по каждому аккаунту/репозиторию/ленте.
- `state.json` продолжает защищать от повторов между ежедневными выпусками, не фиксируя неопубликованные материалы.

**Проверка:** `python -m unittest discover -s tests -v`. Живая доступность сервисов зависит от сети GitHub Actions и правил самих платформ.
